# 专家需求澄清与设计确认

本文件用于新建、资料转化和结构性修改。目标不是让用户从零设计 manifest，而是先利用已有
上下文提出可靠候选，再让用户确认会影响专家行为的关键设计。确认前生成文件会把未验证推断
固化进包，因此必须把设计与开发分开。

## 1. 场景分类

必须进入澄清与确认：

- 新建单专家或专家团；
- 把文档、SOP、仓库、提示词或旧宿主资产转换成专家包；
- 修改专家类型、角色、职责、workflow、技能池或角色技能分配、质量门、权限、MCP 或运行能力。

直接执行：

- 修复由 `expert.json` 与派生物不一致造成的问题；
- 修复路径、格式、字节、模板渲染或便携性缺陷；
- 只读诊断、校验、安装和打包；
- 不引入新产品决策的确定性重生成。

如果一个“修复”需要决定新的职责、角色或能力，把它视为结构性修改。

## 2. 提问前先读取上下文与 question ledger

先从用户消息、附件、已有 `expert.json`、声明资源和可信资料中提取已知信息。确认前只能使用
宿主原生的只读/context API，不能通过 shell、CLI 或其他子进程读取；如果宿主无法无进程读取本地
资料，就只消费消息内上下文，并把本地检查延后到确认后。不要重复询问已经明确的内容。将结果分成：

- **用户事实**：用户明确陈述或可信资料直接支持的内容；
- **候选设计**：为补齐结构而提出、尚待用户确认的内容；
- **未确认项**：当前无法可靠推断且会改变设计的内容。

低影响展示文案可以在候选设计中给出推荐值；职责、workflow、skills 作用、权限和运行能力
不能以未披露假设直接进入生成。

### 会话内 question ledger

进入需求发现时在会话内部维护 ledger，不把它写入 `expert.json`、包、receipt、workspace、ZIP 或
投影。字段、枚举和预算的机器可读真源是
`scripts/manager-contract.json.requirementsDiscovery`；每条记录至少包含：

- `decision_id`：整个会话唯一的语义决定标识；按会改变方案的同一选择归一，不能把“是否存在”、
  “具体是哪份”和“请提供哪份”同一依据来源拆成新决定，也不能通过改写措辞或换 id 重问；
- `source`：用户、可信资料、候选设计或技术映射；
- `status`：未决、已问、已回答、候选、已确认、阻塞或已替代；
- `dependencies`：只记录选择收敛的直接前提：用户明确把决定延期到某项结果之后，或可信证据证明
  该前提会改变下游的候选集合或比较。两个决定只是共享同一个执行权限、成本或安全门时不能连边；
  依赖未知、成环或尚未解决时不得同轮询问真正的下游。前提仍为 `open/asked` 时，下游保持原待决
  状态但不进入当前 question-ready 依赖前沿；
- `asked_via`：未提问、交互工具或正文。同一决定只能选择一个提问渠道；
- `blocked_by`：当前所有可达的根 blocker `decision_id`，排序去重；未知引用保留其引用 id；
- `resume_status`：第一次从 `open/asked` 转为任意阻塞时保存的原状态，不能被后续重算覆盖。

第一次把决定从 `open` 转为 `asked` 时才计入预算，并写定唯一 `asked_via`。已问未答继续保持
`asked`，只能在事实清单或业务卡中标记“等待答复”，不得退回 `open`、换 id、提高问题具体度后重问，
也不得改用另一提问渠道。用户后续补充更新原 `decision_id`；只有用户明确改变先前答案，或原选择
确实分裂出互不相同的业务影响，才更新或派生带原决定依赖的新记录。用户主动补充、资料事实和最终整卡确认不计入。每轮最多
3 个互不依赖的决定；单专家默认最多 2 轮/6 个决定，专家团最多 3 轮/9 个决定。只有安全、权限
或 Connector 阻塞可增加恰好一轮，必须当场解释原因；普通信息不足或用户改变专家类型不能重置
已消耗预算，也不能获得第二次例外。预算耗尽且无法形成安全候选时停止并说明阻塞。

决定如何解决由 `source`、用户明确授权和当前可信证据共同路由，不增加第八个 ledger 字段：用户明确
保留选择权时才提问；用户明确委托管理器时，在候选具备稳定业务标签、会影响决定的可观察差异和
可信 provenance 后提出候选；明确由可信资料决定时，带 provenance 派生而不重问。候选证据不足时
保持 `open`，只询问缺失的比较证据。进入阻塞及恢复时必须保留原 `decision_id`、`source`、用户授权、
`asked_via` 和预算历史，不能借恢复改变谁负责决定。

用户明确最终拒绝某条路径时，将该路径的原决定转为 `blocked` 或 `superseded`；后来出现候选证据不
自动重开，也不能再次询问，除非用户明确修订原决定。条件性延期不是拒绝：只有用户明确给出未来
解决条件（例如“出现经过验证的候选后再决定”）时，才保留原待决决定，并在该条件有证据满足后重算
前沿；不得换 `decision_id`、重置预算或把延期解释为授权。任何权限或目标变化都必须来自用户显式证据。

新决定准入必须先于依赖收敛和 question-ready 前沿计算。不能仅凭“付费推理”、用户提供的供应商/模型等技术词，或假想未来可能使用外部能力，就新建
“是否向组织外发送数据”等决定。只有用户明确把当前数据边界作为现在要决定的事项，或可信资料已
证明存在一个具体、当前候选或执行路径会把数据送出组织，才把该边界作为 question-ready material
decision。候选、账号、入口或 Runtime 绑定被明确延期/阻塞且尚无具体外部路径时，把“当前不得联网
或外发数据”作为只保护联网与数据外发的安全守卫并随现有 blocker 展示；它不占提问预算、不阻止
blocked-card 的 design-only 确认、不新增 `open/asked` 决定，也不询问
假想未来路径。后续出现具体可信外部路径时再带 provenance 记录或更新该决定，不能把安全守卫解释为用户已经同意外发。
用户已经明确允许或禁止当前外发时，正常记录或更新原 material decision。

确认前零副作用边界只覆盖本文件的新建、资料转化和结构性设计流程：允许读取用户消息，以及
宿主原生只读/context API 已提供的可信本地资料，但 shell/CLI、文件写入、联网、进程/preflight、
Plugin 和 MCP 调用数必须都是 0。受控修改、只读诊断、校验、安装和打包走各自合同，不能借用
本指标宣称零执行。

## 3. 需求转译卡与模块推荐

用户不需要先认识 Agent 工程术语。收到模糊需求后，管理器在内部记录以下信息；没有影响方案的
缺口时直接给出推荐，不为填满表格追问：

| 判断项 | 要识别的内容 |
|---|---|
| 内容类型 | 资料、规则、代码、流程、专业职责或外部系统。 |
| 使用方式 | 执行时查阅、始终遵守、Agent 主动调用、事件自动触发或连接外部系统。 |
| 作用范围 | 单个角色、多个角色、整个专家团或整个 workspace。 |
| 副作用 | 只读、本地计算、修改 workspace，或对外部系统读写。 |
| 已有实现 | 本地文件、Git 仓库、现有 Python/Shell 脚本、JS/TS、Connector、MCP，或尚待开发。 |
| 推荐结果 | 推荐模块、理由、置信度，以及唯一必要的确认问题。 |

首次三层回复中的每项推荐都必须写出：白话模块名、使用时机、使用角色或作用范围、推荐理由、
副作用与现有实现状态。不能把这些内容留到后续“业务确认卡”才补，也不能用一句“是否同意
以上方案”替代尚未确认的实现前提。

### 用业务语言选模块

| 用户真正想实现的效果 | 默认推荐 |
|---|---|
| 执行时查阅本地文件、Git 仓库、规则、案例或知识 | 资料库（Reference）。 |
| 给角色一套可复用的方法、清单或 SOP | 能力包（Skill）。 |
| 整个 workspace 始终遵守同一规则 | 共享规则（Instruction）。 |
| 只有指定角色或本专家团遵守一条规则 | 角色规则（role-level Instruction），分配给明确角色。 |
| 反复启动一个有固定步骤和验收标准的任务 | 稳定流程（Workflow），需要时增加快捷入口（Command）。 |
| Agent 主动调用确定性的 JavaScript/TypeScript 能力 | 计算工具（Custom tool）。 |
| 已有 Python/Shell 确定性脚本 | 放进对应能力包，由 Skill script executor 调用。 |
| 工具执行前后自动触发、记录或拦截 | 过程控制（Plugin/Hook）。 |
| 主动查询或修改外部软件、服务、数据库 | 外部连接（MCP）。 |
| 一项可被用户独立询问的专业职责 | 独立 Agent；需要多种职责协作时组成专家团（Team）。 |

允许组合模块。“发布前查询外部审批状态，未通过就阻止发布”需要 `MCP + Plugin`：MCP 查询
审批系统，Plugin 在发布事件发生前执行拦截。不要把连接外部系统本身归给 Plugin。

容易混淆的边界用运行行为来解释：

- Reference 是需要时查阅的资料；Instruction 是始终要遵守的规则。
- Plugin 在事件发生前后自动运行；MCP 由 Agent 主动调用来读写外部系统。
- Custom tool 是 Agent 主动调用的 JS/TS 能力；现有 Python/Shell 脚本放在 Skill 中，由确定性
  executor 运行。
- Reference 的角色分配用于路由和审计，不是访问控制。需要严格隔离时改用角色专属 Skill 或
  带权限的 MCP。

### Reference 来源判断

- 用户提供本地文件或目录：先做零执行检查，不运行脚本、安装命令或 Hook。确认后把可接受的
  UTF-8 文本或安全转换结果复制到 `.opencode/references/<slug>/<alias>/`，最终包不记录绝对路径、
  `~` 或开发机相对路径。PDF、DOCX、图片等二进制不能直接冒充 Reference 文本；无法安全转换时
  说明原因并请用户提供可信文本版本。
- 用户提供 Git 仓库链接：推荐 Git Reference，`repository` 可使用 Git URL、host/path 或 GitHub
  `owner/repo`。`branch` 可选；省略时明确说明将跟随仓库默认分支。管理器确认前不得 clone、fetch
  或探测私有仓库。首次推荐同时列出拟使用的角色；角色分配只用于路由和审计，不是访问控制。
  “什么时候查阅”优先写进 `description`，不要仅为查阅触发条件额外创建角色规则。
- Git Reference 的 `description` 约束 Agent 何时使用资料，不控制宿主何时联网或异步 materialize。
  不得承诺“只有命中触发条件才会联网”。若用户要求触发前绝不连接仓库，改为受控外部连接，
  当前整卡确认前只询问是否已有真实、可用且经核验的业务入口；确认后才在开发细节映射实现渠道。
- `description` 说明什么时候查阅；`hidden` 只隐藏 TUI 的 `@` 自动补全，不保密，也不限制其他
  角色在底层配置中看到该 Reference。
- `repository` 不得夹带密码、Token 或其他嵌入式凭据。私有仓库认证由运行环境的 Git 凭据、
  SSH Agent 或宿主能力负责。只接受远程 Git URL、SCP-like 地址、host/path 或 GitHub
  `owner/repo`；拒绝本地绝对/相对路径、`file:`、query 和 fragment。

### 置信度和确认

- 高置信：给出一个推荐和理由，进入最终确认。
- 中置信：给出两个候选，只问一个能区分运行行为的问题。例如不要问“Custom tool 还是
  Plugin”，改问“由专家主动调用，还是在执行前后自动触发？”
- 低置信：先问用户希望“查阅、始终遵守、主动执行、事件触发，还是连接外部系统”。

自动匹配只提出候选。用户确认前不得生成资源、修改 `expert.json`、拉取 Git、启用代码、连接
外部服务或扩大权限。

## 4. 信息完整性

以下是内部完整性检查，不是默认展示模板。先把业务影响写入业务确认卡；字段、完整技能名、路径、
枚举和运行参数只在用户要求“开发细节”时展示。

### 单专家

开始生成前确认：

- 专家目标、目标用户和成功标准；
- 核心职责、明确不负责的边界；
- 输入、输出，以及是否存在值得固化为顶层 Workflow 的稳定任务合同；没有时明确写“无”；
- 每个可由用户直接触发的稳定 workflow 是否需要 command，以及推荐名称、入口 agent 和输入方式；
- 每项 skill 的来源、完整名称、分配角色、触发时机和预期产物；
- 质量门、异常处理和交付标准；
- 是否需要 MCP、runtime extensions、外部资料和特殊权限。

### 专家团

开始生成前确认：

- 专家团目标、目标用户、输入、最终产物和成功标准；
- 团长的职责、调度方式、验收责任和最终集成流程；
- 每个团员的职责边界、输入、输出和委派条件；
- 每项 skill 的来源、完整名称、触发时机、预期产物和一个或多个使用角色；
- 用户上传技能是目录还是 ZIP；单专家自动分配，专家团必须确认一个、多个或全部成员；
- 若声明 Workflow，确认串行/并行 Phase、角色依赖、handoff、返工和升级流程；parallel 同时确认
  必参与角色集合以及是否允许每个角色按输入动态创建多个实例，但不固定实例数或分片；
- 每个可由用户直接触发的稳定 workflow 是否需要独立 command；默认由团长接收命令并编排；
- 质量门、异常处理、MCP、runtime extensions 和权限。

每一项可以来自用户事实、资料事实或已确认的候选设计，不要求全部由用户原创提供。

### 运行资源检查

在确认运行能力时根据真实需求给出推荐，不要求用户直接填写 manifest：

| 用户需求 | 内部技术映射与按需开发细节 |
|---|---|
| 随包分发的领域资料、规范、案例、知识库或操作手册 | 本地资料使用 `reference_files[]` 与 local `references`；Git 资料使用 `references.<alias>.repository`。同时确认使用角色、`description`、可选 `branch` 和 `hidden`。 |
| 角色或专家团内部始终遵守的规则 | 使用 `role_instructions` 声明包内 Markdown，并由角色 `instructions[]` 显式分配。 |
| 类似 hook 的事件监听、工具拦截或运行时行为修改 | 使用 `plugins.local[]` 生成 `.opencode/plugins/`；需要第三方依赖时同时确认 `.opencode/package.json`。 |
| 供智能体直接调用的 JavaScript/TypeScript 执行能力 | 使用 `custom_tools[]` 生成 `.opencode/tools/`；不要为了单纯可调用工具扩大成 plugin。 |
| 需要对整个 workspace 生效的专家或专家团指令 | 使用 `instruction_files[]` 生成 `.opencode/instructions/<slug>/`，并用 `instructions[]` 把文件或 glob 写入 `opencode.json`。 |
| 主动读写外部软件、服务或数据库 | 使用 `mcp_servers[]`；当前整卡确认前只核对真实可用业务入口，确认后才把入口映射为 Connector、MCP、URL 或启动命令；没有入口时标记外部连接能力仍需开发。 |

推荐外部连接时，首次回复只用业务语言询问目标系统是否已有真实、可用且经核验的业务入口；
assistant 不得在当前整卡确认前的卡、provenance 或卡后问题中枚举 Connector、MCP、URL、启动命令
等实现渠道。用户原话中的技术词只能作为 provenance 事实原样保留，不能据此扩写问题。入口未知时，
这一业务前提优先于笼统的方案确认；确认不存在时标记“外部连接能力仍需开发”，并阻止具体连接
选择和执行。业务选择完成且当前整卡确认后，才在开发细节映射并核验具体实现渠道。用户回答“有”
不等于 Runtime 证据，没有可信入口与宿主运行证据时不得绑定或声称已连接。
外部写权限尚未确认时默认只读最小权限，不要求用户先开放写权限。

本地 plugins 与 custom tools 由 OpenCode 自动发现，不写入根级 `plugin` 或 `tools`；只有 npm
plugins 写入 `opencode.json.plugin`。专家包不开发 `AGENTS.md`。角色规则只写入被分配角色的
Agent Markdown，不进入 workspace 全局 `opencode.json.instructions`。上述能力的业务影响必须出现在业务确认卡中，技术绑定按需进入开发细节；不要让 generator 或 validator
根据附件、描述或目录名自动补建。

### Agent 运行参数

`steps` 是 OpenCode 正式支持且新设计唯一询问、展示和写入的步数字段。不得把 MobileWork
`expert.json` 为旧包保留的 `max_turns`、`maxTurns` 输入兼容名描述为 OpenCode 选项；读取旧 manifest
时静默归一化为 `steps` 即可。`model`、`variant`、`temperature`、`top_p`、`hidden`、`options`
都是可选项：只有用户提出特定模型、成本控制、输出确定性、创造性、隐藏团员或 provider-specific
能力时才询问；普通专家设计不主动逐项盘问，也不在 generator 中猜测。给出推荐时说明未声明项
将继承 OpenCode、模型或 provider 默认值，并建议通常只调整 `temperature` 与 `top_p` 中一个。

### 执行约束发现

出现财务、合规、审计、批量、高风险、重复运行、结果一致、机器可验证，或已有 SOP、模板、脚本、
custom tool、MCP tool 时，内部优先选择受约束的执行方式；业务卡直接说明必须遵守的步骤、决定权和
停止条件，不给它贴自主度等级。先从现有材料中提取事实，再为每个执行单元形成最少约束矩阵：

| 约束 | 只确认什么 |
|---|---|
| 决策边界 | Agent 能自行决定到什么程度 |
| 执行器 | 必须或允许使用哪个脚本、工具或 Agent |
| 执行标准 | 依据哪个规范、阈值、模板、分支规则或确认点 |
| 验收标准 | 什么结果才算完成 |

只有用户任务存在稳定、可复用的执行与验收边界时才声明顶层 Workflow。声明后先设置 workflow
默认值；phase 只有边界不同时才询问；Agent override 只有同一 phase 中角色边界不同时才询问。
不声明 Workflow 时使用普通 Todo 规划，不发明正式 Phase 或 acceptance。只针对阻塞项提问。

以下等级只用于内部技术映射和当前整卡确认后的开发细节，不是业务卡标签。推荐顺序：已有可靠脚本或 custom tool 用“极低（`scripted`）”；固定 SOP 用“低（`fixed`）”；
多个批准方法用“中（`bounded`）”；需要探索但关键决定要确认时用“高（`guided`）”；开放研究
或创意才用“极高（`adaptive`）”。能够机械化
的阶段原则上不得使用 `guided` 或 `adaptive`；确需提高时，业务卡只展示为何需要探索、哪些决定仍需确认等
可观察行为，不能出现“低自主度”“高自主度”或任何相对等级标签；枚举映射只放开发细节。

同一任务既有确定性脚本又有固定 SOP 时先判断执行边界：若脚本拥有全部已确认步骤，业务层明确
说明“全部固定步骤由该脚本执行，不另设 Agent 编排层”；用户要求开发细节时才映射为仅
`scripted` 执行，不凭空增加独立 `fixed` 层。若 Agent 仍需按另行确认的 SOP 准备输入、调用脚本、检查退出
状态和验收结果，则分别描述 `scripted` 执行单元与 `fixed` 编排层，不能用一个 autonomy 值折叠
两层。执行标准必须来自用户或可信资料。权威依据来源和可执行规则值始终使用两个独立的
`decision_id`：前者回答依据哪份制度、版本或可信资料，后者回答实际执行的数值、公式或可计算规则。
两者都已 question-ready 且互不依赖时才可同轮分别提问，不能合并为一个决定；用户明确说明规则值
由权威来源定义时，后者依赖前者并分轮处理。提供来源只解决来源决定，不会在没有制度正文、明确条款
或其他显式证据时自动解决规则值；不得从制度名称、版本、零容差、行业惯例或其他默认值推断规则。
若来源已经回答，但可信材料中没有数值、比例、公式或其他可计算规则，来源决定保持 `answered`，原
规则值决定保持 `open/asked` 并重新计算 question-ready 前沿。此时只询问谁有权提供的显式可计算
规则，不重问来源、不请求整卡确认、不改变规则目标，也不把“没有规则”自动解释为零容差或管理器默认值。
尚未提问时决定为 `open`，一经提问但未回答就
保持 `asked`；两种状态下执行都保持阻塞。用户明确说明某项运行前提或能力不存在、不可用或尚未
建立时，把该前提转为 `blocked`，并沿 `dependencies` 收敛只用于配置或绑定该前提的下游
`open/asked`：这些下游同样转为 `blocked`，不再算当前待决。仍可在当前独立回答且会改变业务卡的
决定继续保持 `open/asked`，不能因存在任意 blocker 就一并吞掉。收敛时保留原 `decision_id`、
`asked_via` 和已消耗预算；前提恢复后继续使用原决定，不新建 id、不重复计费，也不改写后重问。

阻塞闭包和“当前可问什么”是两道不同的门。全图有效且完成阻塞收敛后，只有状态为 `open`，并且
全部传递前提都已经是 `answered/proposed/confirmed` 的决定，才是当前 question-ready root。前提仍为
`open/asked` 时，下游不能提前显示问号、选择项、请求回答的祈使句或技术绑定候选；它保持待决，
不转成 `blocked`，也不消耗提问预算。每轮从当前前沿按 ledger 稳定顺序处理额度内所有互不依赖的
ready 根（最多三个），不能在处理第一个后无故停止。无关的 `asked` 只携带等待状态，不抑制其他 ready
根。完整业务卡渲染后，question-ready 业务选择优先于整卡确认，不能被“先确认整卡”或“开发细节
尚未开放”继续延后。用户明确保留选择权时提问；用户明确委托时基于充分可信候选证据提出候选；
可信资料明确决定时带 provenance 派生。若候选缺少稳定业务标签、会影响决定的可观察差异或可信
provenance，只询问缺失的比较证据，不要求用户盲选，也不宣称候选已经 Runtime 验证。若仍有 pending
但当前没有 question-ready `open`，只携带等待或延后状态，不请求整卡确认。

所有独立 material decision 仍受执行门统一约束：任一 `open/asked/blocked`，或当前整卡尚未确认，
都阻止生成和执行；这条全局门不属于 question frontier，不能据此创建 `dependencies`。用户已经明确
要求现在决定外发边界，或具体可信候选/执行路径证明会向外部发送数据时，“是否允许向外部推理服务
发送数据”须保持未决、被询问并阻止执行；若模型候选的比较不因该答案改变，它不依赖也不阻塞
“选哪类模型”或“选哪个已知入口”。没有具体外部路径时不从付费意图派生这个问题，并继续禁止联网
和外发。只有候选本身的数据保留、出境或导出边界不同、答案会改变候选集合或比较时，数据边界才是模型选择的真实前提。

例如 `runtime-binding.dependencies = [account-available, cost-boundary]`：账号可用性和成本边界仍
未回答时，只询问这两个业务根决定，不询问供应商、模型或具体绑定。`connector-binding` 依赖
`usable-external-entry` 时，只先确认是否存在真实可用的连接入口，不提前要求选择连接实现或字段映射。
用户明确说明根前提尚未建立后，才按 blocker closure 把这些根及其可达下游转为 `blocked`。前提恢复且
可信候选证据充分后，可以在卡后用稳定业务标签和成本、能力、数据边界、权限等可观察差异询问或提出
当前业务选择；provider ID、URL、配置、凭据、字段映射和其他实现绑定细节仍须等待业务选择完成且
当前整卡确认后再展开。

对已声明 Workflow，以下情况不得生成：`scripted` 没有真实确定性执行器；`fixed` 没有 SOP 或分支规则；`bounded`
没有允许范围；`guided` 没有关键确认点；phase 没有验收标准；executor 或业务标准仍是猜测。
用户说“你来决定”时可以形成候选，但不能凭空发明外部业务标准或跳过最终确认。

## 5. 提问与新手输出

按以下顺序推进，仅询问缺失内容：

1. 目标、目标用户和成功标准；
2. 专家类型与角色结构；
3. 各角色职责与边界；
4. 输入、输出、是否声明 workflow；若声明，再确认 Phase、对应 commands、handoff 和返工；
5. 统一 skills、来源、完整名称及角色分配；
6. 质量门、运行能力、权限和环境依赖。

优先使用当前宿主提供的 ask-user-question 工具。工具支持批量问题时，每轮最多组织 3 个
来自当前 question-ready 依赖前沿且互不依赖的决定；每个 question 对象只问一个决定。使用工具后，正文只解释背景和推荐，不得再次
列出或改写同一问题。工具不可用时才在正文提问，整轮只写一个精炼的业务组合问题，不得用编号、
分号或并列问句伪装多个问题；它可以邀请用户一次补充当前全部互不依赖的 missing facts，但不能列成
多个独立问题。依赖前一答案的问题必须分轮，不能因为同一回复也询问了前提就顺带询问其下游。每轮结束后更新 ledger；仍可独立回答的 `asked` 决定只携带“等待答复”状态，不再
显示问号、选择项或请求回答的祈使句，也不得压住同一轮其他互不依赖的 question-ready `open`。
额度允许时必须继续处理这些 ready 根。依赖已阻塞前提的旧问题先按第 4 节收敛，不得继续用“等待
答复”阻塞当前卡。已知、已问、已回答、候选或已确认的决定均不得重新进入 `asked`。

`asked_via` 只是 Agent 会话内记账，不能证明宿主实际只使用一个提问渠道。任何 interaction-channel
评测都必须读取覆盖完整的 host question-channel ledger；缺少宿主事件时精确标记 `not-verified`。
Skill 正文和 assistant 自述都不能充当 host evidence。

能从上下文得到的答案直接写入事实清单。用户不熟悉专家结构时，不要求其填写 schema；先给出
业务语言的推荐方案，再请其选择或修订。

在正文提问时默认使用三层回复；若问题已由交互工具提出，第三层只说明“请在交互卡中回答”，
不重复问题：

```markdown
## 我理解的需求
...

## 建议方案及原因
...

## 只需你确认的事项
1. ...
```

正文先说“资料库、能力包、共享规则、稳定流程、快捷入口、计算工具、过程控制、外部连接”等
白话名称。技术名只在当前整卡确认且用户要求开发细节后，第一次出现时括注一次。Schema 字段、JSON 路径、哈希、receipt、sidecar、
权限和自主度枚举统一放到“开发细节”；用户没有要求时不展开。

校验失败先写清问题、对结果的影响和建议动作，再把原始 finding 放进开发细节。不要删除合同、
财务、医疗等业务本身需要的专业词，只降低 Agent 工程术语密度。

## 6. 候选方案

没有实质分歧时给出一个推荐候选。存在会显著改变角色数量、职责边界、工作流、权限或成本的
分歧时，给出 2–3 个真实可行的方案，并说明取舍与推荐理由。

用户说“你来决定”“不要问，直接做”时，把普通缺口转为明确标记的完整候选，不再提出普通
发现问题，只展示业务候选并保留一次最终整卡确认。不能凭空发明外部业务标准；若安全、权限或
Connector 确实阻塞，只能按例外预算增加一轮并说明原因。这种授权不能替代设计确认，也不能
替代覆盖、安装升级或 zip 替换的 `--force` 确认。

## 7. 业务确认卡与开发细节

澄清完成后默认只展示业务确认卡。所有影响行为、权限、成本或运行前提的决定都必须出现，包括
明确的“无”；不能把新决定藏在开发细节中。

```markdown
# 业务确认卡

## 目标与成功标准
- 目标：...
- 成功标准：...

## 角色与职责
| 角色 | 负责 | 不负责 | 交接对象 |
|---|---|---|---|

## 输入与输出
- 输入：...
- 输出：...

## 稳定流程
- 固定步骤、并行协作、交接与返工：无 / ...

## 资料与能力
- 需要查阅的资料、遵守的规则和可复用能力：无 / ...

## 外部连接
- 外部系统、已有连接器和运行前提：无 / ...

## 读写、联网、权限与成本边界
- 本地/外部读写、联网时机、账号权限、付费能力和资源消耗：...

## 质量门与异常处理
- 验收、证据、停止条件、返工和升级：...

## 信息来源（provenance 附录，不计入八个业务区段）
- 用户事实：...
- 候选设计：...
- 未确认项：无 / ...
```

“资料与能力”必须为每项能力给出清楚的业务能力名称，以及负责或使用它的角色；不能只写“若干
能力包”或数量。机器 Skill 标识和完整文件名属于开发细节，只有用户要求时才展示。业务名称与
角色归属用于确认职责，机器标识只用于后续投影，两者不能混成同一个确认要求。

### 默认展示边界

默认展示面覆盖业务确认卡、provenance 附录，以及当前整卡确认前的卡后提问。即使用户已经要求
“展开开发细节”，只要同一回复因 material impact 使旧确认失效，这整个展示面仍须使用业务语言，
直到用户明确确认当前整卡。完整卡后允许处理 question-ready 的可信业务候选，但只展示稳定业务
标签和会影响决定的可观察差异。此时不得输出 manifest 字段、路径、hash、receipt、sidecar、机器
Skill 标识、权限或自主度枚举、这些枚举的中文等级标签，以及 provider ID、URL、配置、凭据、字段
映射、Connector/MCP/启动命令等实现渠道或其他实现绑定细节。用户消息中已经出现的技术词可以在
provenance 中原样记录为用户事实，但不能借此提前展开上述实现细节，也不能复用为 assistant 撰写的确认问题。

隐藏分类不等于隐藏影响。业务卡必须写清：谁能决定；哪些步骤必须按已确认规则执行、哪些允许
有限选择；哪里需要再次确认；允许哪些本地或外部副作用；何时停止、返工或升级。不要写“低自主度
固定流程”，应写“按已确认步骤逐项执行，不自行增加规则、跳过检查或放宽验收；缺证据时返工，
仍不足时停止并交用户处理”。“固定步骤”“稳定流程”等普通业务词可以使用，禁止的是把流程贴上
内部等级或枚举标签。

业务卡完成后先在内部做技术映射。会改变业务设计的字段必须追溯到状态为 `answered`、`proposed`
或 `confirmed` 的 `decision_id`；确定性的 hash、路径、receipt、schema、sidecar 和投影字段追溯到
manager contract 或已确认的技术规则，不虚构新的用户决定。

### `full-card-first` 响应门

任何影响行为、权限、成本或运行前提的决定新增、改变或状态更新都触发本门。它既包括技术映射
发现新的联网、账号、Connector 或 Runtime 前提，也包括用户改动已确认选择，以及执行准备阶段
发现某项前提不可用。不得把“只是更新状态”当作继续沿用旧确认的理由。

触发后必须在**同一条 assistant 回复**按以下顺序处理，而且这段序列必须是回复的**第一块内容**：

1. 在 ledger 中记录或更新原 `decision_id`，先明确告知旧确认已失效；
2. 尾随动作判定前先做依赖收敛：把明确不可用或尚未建立的前提转为 `blocked`，再沿
   `dependencies` 做传递可达闭包；边必须来自用户显式延期，或可信证据证明前提会改变候选集合/
   比较，不能来自共享执行权限门。所有可达的下游 `open/asked` 都转为 `blocked`。完成全图校验和
   blocker closure 后另算 question-ready 依赖前沿：只有 `open` 且全部传递前提均为
   `answered/proposed/confirmed` 的决定可以提问；前提仍为 `open/asked` 的下游保持待决但不可问；
3. 把收敛后的 `open/asked/answered/proposed/confirmed/blocked` 状态合并进卡；
4. 立即完整重发八个业务区段和 provenance 附录，未变化区段也必须保留；
5. 整卡之后才执行一种尾随动作：
   - 收敛后仍有 `open/asked` 待决项：在每轮额度内处理当前依赖前沿中全部互不依赖的 `open`，不能
     因一个无关 `asked` 提前停止，也不能先请求整卡确认或以
     开发细节尚未开放为由延后。用户明确保留选择权时首次提问；用户明确委托时基于充分可信候选
     证据提出候选；可信资料明确决定时带 provenance 派生。证据不足时只询问缺失的比较证据；
     `asked` 只携带等待状态，未就绪下游只说明待前提明确后再决定。即使当前没有可问决定，也不请求整卡确认；
   - 收敛后没有待决项：只请求一次当前整卡的 design-only 确认。其余项即使为 `blocked` 也属于此分支，
     并须说明确认只冻结设计与阻塞状态，不能授权生成。

在上述失效说明和整卡之前，禁止输出开发确认卡、开发细节、架构或技术绑定、阻塞摘要、实现
选项；不能先解释技术方案再补卡，也不能只说稍后更新。当前整卡获得确认前，即使用户已要求
开发细节，也必须延后展开完整技能名、Workflow、`workflows[].command`、`$ARGUMENTS`、Agent
入口、路径、枚举、等级标签、provider ID、URL、配置、凭据、字段映射、receipt、sidecar 和投影规则。
外部入口问题不得枚举 Connector、MCP、URL、启动命令等实现渠道；只问是否已有真实、可用且经核验的
业务入口。这不禁止在卡后用稳定业务标签和可观察差异处理已 question-ready 的可信候选；业务选择完成且当前
整卡确认后，才展开实现绑定细节。该限制也覆盖 provenance 和卡后提问。解除阻塞并重新确认前继续禁止生成。
任一 `open/asked/blocked` material decision 或尚未确认的当前整卡都继续阻止生成与执行；该执行门
不参与 question-ready 前沿计算，不能反向吞掉仍可询问或提出候选的独立决定。

`d.dependencies = [p]` 表示 p 是 d 的直接前提，传播方向为 `p → d`。每次尾随动作前从完整 ledger
重新计算全图，而不是在旧 `blocked_by` 上增量追加。链 `A → B → C` 中 A 阻塞时，仍为
`open/asked` 的 B、C 都阻塞；一个决定同时依赖多个前提时，`blocked_by` 聚合全部可达根 blocker，
只恢复其中一个时仍保持阻塞。显式不可用的根 blocker 把自身 `decision_id` 写入自己的 `blocked_by`，
全图重算不得自行清除；只有新的用户事实或可信资料明确解决原决定时才能移除。第一次从
`open/asked` 变为任意阻塞时把原状态写入 `resume_status`；派生节点只有 `blocked_by` 为空、所有引用
存在且全图不成环时才恢复。阻塞与恢复始终保留原 `decision_id`、`source`、用户授权、提问渠道和
预算历史。恢复 `asked` 只携带原等待状态，不能重问；与任何 blocker 都无
可达路径的独立决定不受影响。重算必须对 ledger 和 dependencies 顺序稳定、幂等。

Question-ready root 与 blocker root 是不同概念。前者是当前可以向用户提问的依赖前沿，后者是
`blocked_by` 中解释阻塞来源的根。链 `A(open) → B(open)` 中只问 A，B 保持 `open` 但不展示问题；
A 变为 `asked` 时只携带 A 的等待状态，仍不问 B，也不确认整卡；A 变为 `answered/proposed/confirmed`
后，B 才进入下一轮前沿。若 C 同时依赖独立的 A、B，本轮只问 A、B；只解决其中一个时 C 仍不可问。
同一回复刚提出根问题并不等于其已解决，因此不得在该回复顺带询问下游。前提恢复后的可信业务
候选选择在完整卡后立即按授权处理；当前整卡确认不是它进入前沿的附加前提。provider ID、URL、
配置、凭据、字段映射及连接实现等绑定细节，只有业务选择完成且当前整卡确认后才可进入开发细节。

未知 dependency 产生 `REQUIREMENTS_UNKNOWN_DEPENDENCY`，自环或任意环产生
`REQUIREMENTS_DEPENDENCY_CYCLE`；受影响待决节点及其可达待决下游 fail-safe 转为 blocked，但这类
结构错误不能伪装成普通业务阻塞。仍须先重发完整卡，卡后只报告稳定诊断，不请求整卡确认、不生成；
修复图并再次完整收敛后，才按 pending/no-pending 分支继续。

用户回答后把相应决定转为 `answered/proposed`；明确无法提供、能力不存在或前提尚未建立时，先把
该前提及依赖它的所有可达下游决定收敛为 `blocked`，再在同一回复执行完整 `full-card-first` 序列。阻塞恢复
时更新原决定并重新执行该序列，不换 id、不改变 source 或用户授权、不重复计费或重问；恢复后的
question-ready 决定仍按“用户选择、明确委托、可信资料派生”路由。用户最终确认当前整张业务卡后，把卡内当前
`answered`/`proposed` 业务决定一并提升为 `confirmed`。

确认后、执行前按实际任务选择环境 feature；纯咨询与设计确认没有 feature，也不运行 core
preflight：

| 任务 | feature |
|---|---|
| 生成 | `core`、`git` |
| 校验或普通导入 | `core` |
| Excel Reference 导入 | `core`、`excel` |
| 打包 | `core`、`package` |
| DOCX bundle | `core`、`bundle-docx` |
| 可信配置证据 | `core`、`config-load`，显式 sidecar 与目标/host contract |
| 评测 | `core`、`coverage` |

表中的多个 feature 表示重复传入 `--feature`，不是把 `+` 拼进一个参数；例如生成任务使用
`--feature core --feature git`。

最后仍只通过工具或正文之一确认整张卡：纯咨询或仅设计请求询问“是否确认这份业务设计？”，确认
后交付设计并停止；用户已明确要求生成时询问“是否确认按此业务确认卡开始生成？”，只有明确同意
才能运行 preflight、创建 manifest 或调用生成器。最终确认不计入提问预算。输入完整但尚未确认时
直接展示业务卡，不人为增加访谈；用户已经对同一完整设计明确确认时，不重复确认或提问。此时若
任务没有 feature 就交付并停止；只有明确的执行任务才进入确认后执行通道。

底层 generator 不接收可信的人类确认凭证，因而本门是 Agent 行为合同，不是机器 attestation。
模型自行产生的 `confirmed: true` 不能升级为用户确认；真正的强门需要 Desktop 绑定 user event、
proposal/session id 与 manifest hash 的 host attestation，属于独立产品能力。

command 是可选的用户入口，不是 workflow 本体的第二份真相源。为每个可由用户直接触发、会重复
使用的稳定 workflow 默认推荐一个 `workflows[].command`；多个这类 workflow 分别推荐多个 command。内部
handoff、单个 phase 和一次性流程不单独创建。用户明确不需要 command 时，在业务确认卡中写明原因，
不要让 validator 或生成器自动补建。

## 8. 结构性修改

先展示设计差异：

```markdown
| 设计项 | 修改前 | 候选修改后 | 原因与影响 |
|---|---|---|---|
```

确认后修改 `expert.json` 并整体重建派生物。用户在确认后又改变角色、workflow、skills 或权限时，
返回澄清阶段，并按第 7 节 `full-card-first` 门在同一回复先声明旧确认失效、重发完整业务确认卡，
再处理待决问题或当前整卡确认；不得先展示差异表、开发细节或实现选项。

旧包使用 `common_skills` 和 purpose 对象时，结构性修改必须先迁移：不重命名、不改写现有技能
文件，把旧通用技能分配给全部角色，把旧角色技能保留给原角色，再基于统一技能池继续设计。
`origin: uploaded` 且 `edit_policy: preserved` 的技能默认不得修改；若用户明确授权修改包内副本，
业务确认卡必须展示其可编辑性变化，`managed` 与 `origin: uploaded` 映射按需放开发细节。

## 9. 阻塞与冲突

- 用户答案互相矛盾：指出冲突并询问，不自行选择。
- 用户暂时无法回答：给出推荐候选并标记来源，不把候选描述成事实。
- 用户拒绝确认：停止生成，可以继续展示或修订草案。
- 目标已存在：设计确认后再处理独立的 `--force` 覆盖确认。
- 诊断中发现需要产品决策：先完成只读报告；若用户要求修复，再转入结构性修改流程。
