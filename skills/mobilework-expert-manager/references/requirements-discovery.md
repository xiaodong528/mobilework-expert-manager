# 专家需求澄清与设计确认

本文件用于新建、资料转化和结构性修改。目标不是让用户从零设计 manifest，而是先利用已有
上下文提出可靠候选，再让用户确认会影响专家行为的关键设计。确认前生成文件会把未验证推断
固化进包，因此必须把设计与开发分开。

## 1. 场景分类

必须进入澄清与确认：

- 新建单专家或专家团；
- 把文档、SOP、仓库、提示词或旧宿主资产转换成专家包；
- 修改专家类型、角色、职责、workflow、技能池或角色技能分配、质量门、权限、MCP 或运行能力。

直接执行：

- 修复由 `expert.json` 与派生物不一致造成的问题；
- 修复路径、格式、字节、模板渲染或便携性缺陷；
- 只读诊断、校验、安装和打包；
- 不引入新产品决策的确定性重生成。

如果一个“修复”需要决定新的职责、角色或能力，把它视为结构性修改。

## 2. 提问前先读取上下文

先从用户消息、附件、已有 `expert.json`、声明资源和可信资料中提取已知信息。不要重复询问
已经明确的内容。将结果分成：

- **用户事实**：用户明确陈述或可信资料直接支持的内容；
- **候选设计**：为补齐结构而提出、尚待用户确认的内容；
- **未确认项**：当前无法可靠推断且会改变设计的内容。

低影响展示文案可以在候选设计中给出推荐值；职责、workflow、skills 作用、权限和运行能力
不能以未披露假设直接进入生成。

## 3. 需求转译卡与模块推荐

用户不需要先认识 Agent 工程术语。收到模糊需求后，管理器在内部记录以下信息；没有影响方案的
缺口时直接给出推荐，不为填满表格追问：

| 判断项 | 要识别的内容 |
|---|---|
| 内容类型 | 资料、规则、代码、流程、专业职责或外部系统。 |
| 使用方式 | 执行时查阅、始终遵守、Agent 主动调用、事件自动触发或连接外部系统。 |
| 作用范围 | 单个角色、多个角色、整个专家团或整个 workspace。 |
| 副作用 | 只读、本地计算、修改 workspace，或对外部系统读写。 |
| 已有实现 | 本地文件、Git 仓库、现有 Python/Shell 脚本、JS/TS、Connector、MCP，或尚待开发。 |
| 推荐结果 | 推荐模块、理由、置信度，以及唯一必要的确认问题。 |

首次三层回复中的每项推荐都必须写出：白话模块名、使用时机、使用角色或作用范围、推荐理由、
副作用与现有实现状态。不能把这些内容留到后续“专家设计确认稿”才补，也不能用一句“是否同意
以上方案”替代尚未确认的实现前提。

### 用业务语言选模块

| 用户真正想实现的效果 | 默认推荐 |
|---|---|
| 执行时查阅本地文件、Git 仓库、规则、案例或知识 | 资料库（Reference）。 |
| 给角色一套可复用的方法、清单或 SOP | 能力包（Skill）。 |
| 整个 workspace 始终遵守同一规则 | 共享规则（Instruction）。 |
| 只有指定角色或本专家团遵守一条规则 | 角色规则（role-level Instruction），分配给明确角色。 |
| 反复启动一个有固定步骤和验收标准的任务 | 稳定流程（Workflow），需要时增加快捷入口（Command）。 |
| Agent 主动调用确定性的 JavaScript/TypeScript 能力 | 计算工具（Custom tool）。 |
| 已有 Python/Shell 确定性脚本 | 放进对应能力包，由 Skill script executor 调用。 |
| 工具执行前后自动触发、记录或拦截 | 过程控制（Plugin/Hook）。 |
| 主动查询或修改外部软件、服务、数据库 | 外部连接（MCP）。 |
| 一项可被用户独立询问的专业职责 | 独立 Agent；需要多种职责协作时组成专家团（Team）。 |

允许组合模块。“发布前查询外部审批状态，未通过就阻止发布”需要 `MCP + Plugin`：MCP 查询
审批系统，Plugin 在发布事件发生前执行拦截。不要把连接外部系统本身归给 Plugin。

容易混淆的边界用运行行为来解释：

- Reference 是需要时查阅的资料；Instruction 是始终要遵守的规则。
- Plugin 在事件发生前后自动运行；MCP 由 Agent 主动调用来读写外部系统。
- Custom tool 是 Agent 主动调用的 JS/TS 能力；现有 Python/Shell 脚本放在 Skill 中，由确定性
  executor 运行。
- Reference 的角色分配用于路由和审计，不是访问控制。需要严格隔离时改用角色专属 Skill 或
  带权限的 MCP。

### Reference 来源判断

- 用户提供本地文件或目录：先做零执行检查，不运行脚本、安装命令或 Hook。确认后把可接受的
  UTF-8 文本或安全转换结果复制到 `.opencode/references/<slug>/<alias>/`，最终包不记录绝对路径、
  `~` 或开发机相对路径。PDF、DOCX、图片等二进制不能直接冒充 Reference 文本；无法安全转换时
  说明原因并请用户提供可信文本版本。
- 用户提供 Git 仓库链接：推荐 Git Reference，`repository` 可使用 Git URL、host/path 或 GitHub
  `owner/repo`。`branch` 可选；省略时明确说明将跟随仓库默认分支。管理器确认前不得 clone、fetch
  或探测私有仓库。首次推荐同时列出拟使用的角色；角色分配只用于路由和审计，不是访问控制。
  “什么时候查阅”优先写进 `description`，不要仅为查阅触发条件额外创建角色规则。
- Git Reference 的 `description` 约束 Agent 何时使用资料，不控制宿主何时联网或异步 materialize。
  不得承诺“只有命中触发条件才会联网”。若用户要求触发前绝不连接仓库，改为受控外部连接，
  并按 Connector/MCP、URL 或启动命令确认实现前提。
- `description` 说明什么时候查阅；`hidden` 只隐藏 TUI 的 `@` 自动补全，不保密，也不限制其他
  角色在底层配置中看到该 Reference。
- `repository` 不得夹带密码、Token 或其他嵌入式凭据。私有仓库认证由运行环境的 Git 凭据、
  SSH Agent 或宿主能力负责。只接受远程 Git URL、SCP-like 地址、host/path 或 GitHub
  `owner/repo`；拒绝本地绝对/相对路径、`file:`、query 和 fragment。

### 置信度和确认

- 高置信：给出一个推荐和理由，进入最终确认。
- 中置信：给出两个候选，只问一个能区分运行行为的问题。例如不要问“Custom tool 还是
  Plugin”，改问“由专家主动调用，还是在执行前后自动触发？”
- 低置信：先问用户希望“查阅、始终遵守、主动执行、事件触发，还是连接外部系统”。

自动匹配只提出候选。用户确认前不得生成资源、修改 `expert.json`、拉取 Git、启用代码、连接
外部服务或扩大权限。

## 4. 信息完整性

### 单专家

开始生成前确认：

- 专家目标、目标用户和成功标准；
- 核心职责、明确不负责的边界；
- 输入、输出，以及是否存在值得固化为顶层 Workflow 的稳定任务合同；没有时明确写“无”；
- 每个可由用户直接触发的稳定 workflow 是否需要 command，以及推荐名称、入口 agent 和输入方式；
- 每项 skill 的来源、完整名称、分配角色、触发时机和预期产物；
- 质量门、异常处理和交付标准；
- 是否需要 MCP、runtime extensions、外部资料和特殊权限。

### 专家团

开始生成前确认：

- 专家团目标、目标用户、输入、最终产物和成功标准；
- 团长的职责、调度方式、验收责任和最终集成流程；
- 每个团员的职责边界、输入、输出和委派条件；
- 每项 skill 的来源、完整名称、触发时机、预期产物和一个或多个使用角色；
- 用户上传技能是目录还是 ZIP；单专家自动分配，专家团必须确认一个、多个或全部成员；
- 若声明 Workflow，确认串行/并行 Phase、角色依赖、handoff、返工和升级流程；parallel 同时确认
  必参与角色集合以及是否允许每个角色按输入动态创建多个实例，但不固定实例数或分片；
- 每个可由用户直接触发的稳定 workflow 是否需要独立 command；默认由团长接收命令并编排；
- 质量门、异常处理、MCP、runtime extensions 和权限。

每一项可以来自用户事实、资料事实或已确认的候选设计，不要求全部由用户原创提供。

### 运行资源检查

在确认运行能力时根据真实需求给出推荐，不要求用户直接填写 manifest：

| 用户需求 | 写入确认稿的实现细节 |
|---|---|
| 随包分发的领域资料、规范、案例、知识库或操作手册 | 本地资料使用 `reference_files[]` 与 local `references`；Git 资料使用 `references.<alias>.repository`。同时确认使用角色、`description`、可选 `branch` 和 `hidden`。 |
| 角色或专家团内部始终遵守的规则 | 使用 `role_instructions` 声明包内 Markdown，并由角色 `instructions[]` 显式分配。 |
| 类似 hook 的事件监听、工具拦截或运行时行为修改 | 使用 `plugins.local[]` 生成 `.opencode/plugins/`；需要第三方依赖时同时确认 `.opencode/package.json`。 |
| 供智能体直接调用的 JavaScript/TypeScript 执行能力 | 使用 `custom_tools[]` 生成 `.opencode/tools/`；不要为了单纯可调用工具扩大成 plugin。 |
| 需要对整个 workspace 生效的专家或专家团指令 | 使用 `instruction_files[]` 生成 `.opencode/instructions/<slug>/`，并用 `instructions[]` 把文件或 glob 写入 `opencode.json`。 |
| 主动读写外部软件、服务或数据库 | 使用 `mcp_servers[]`；先确认是否已有 Connector、URL 或启动命令，没有时明确说明需要开发连接器。 |

推荐外部连接时，首次回复的确认项必须覆盖已有 Connector、MCP、URL 或启动命令中的实际可用
入口。入口未知时，这一项优先于笼统的方案确认；确认不存在时明确标记“需要开发连接器”，不能
把设计候选写成已经可连接。外部写权限尚未确认时默认只读最小权限，不要求用户先开放写权限。

本地 plugins 与 custom tools 由 OpenCode 自动发现，不写入根级 `plugin` 或 `tools`；只有 npm
plugins 写入 `opencode.json.plugin`。专家包不开发 `AGENTS.md`。角色规则只写入被分配角色的
Agent Markdown，不进入 workspace 全局 `opencode.json.instructions`。上述能力必须出现在设计确认稿中；不要让 generator 或 validator
根据附件、描述或目录名自动补建。

### Agent 运行参数

`steps` 是 OpenCode 正式支持且新设计唯一询问、展示和写入的步数字段。不得把 MobileWork
`expert.json` 为旧包保留的 `max_turns`、`maxTurns` 输入兼容名描述为 OpenCode 选项；读取旧 manifest
时静默归一化为 `steps` 即可。`model`、`variant`、`temperature`、`top_p`、`hidden`、`options`
都是可选项：只有用户提出特定模型、成本控制、输出确定性、创造性、隐藏团员或 provider-specific
能力时才询问；普通专家设计不主动逐项盘问，也不在 generator 中猜测。给出推荐时说明未声明项
将继承 OpenCode、模型或 provider 默认值，并建议通常只调整 `temperature` 与 `top_p` 中一个。

### 执行约束发现

出现财务、合规、审计、批量、高风险、重复运行、结果一致、机器可验证，或已有 SOP、模板、脚本、
custom tool、MCP tool 时，主动推荐低自主度。先从现有材料中提取事实，再为每个执行单元形成
最少约束矩阵：

| 约束 | 只确认什么 |
|---|---|
| 自主度 | Agent 能自行决定到什么程度 |
| 执行器 | 必须或允许使用哪个脚本、工具或 Agent |
| 执行标准 | 依据哪个规范、阈值、模板、分支规则或确认点 |
| 验收标准 | 什么结果才算完成 |

只有用户任务存在稳定、可复用的执行与验收边界时才声明顶层 Workflow。声明后先设置 workflow
默认值；phase 只有边界不同时才询问；Agent override 只有同一 phase 中角色边界不同时才询问。
不声明 Workflow 时使用普通 Todo 规划，不发明正式 Phase 或 acceptance。只针对阻塞项提问。

推荐顺序：已有可靠脚本或 custom tool 用“极低（`scripted`）”；固定 SOP 用“低（`fixed`）”；
多个批准方法用“中（`bounded`）”；需要探索但关键决定要确认时用“高（`guided`）”；开放研究
或创意才用“极高（`adaptive`）”。能够机械化
的阶段原则上不得使用 `guided` 或 `adaptive`；确需提高时必须在确认稿中展示原因。

对已声明 Workflow，以下情况不得生成：`scripted` 没有真实确定性执行器；`fixed` 没有 SOP 或分支规则；`bounded`
没有允许范围；`guided` 没有关键确认点；phase 没有验收标准；executor 或业务标准仍是猜测。
用户说“你来决定”时可以形成候选，但不能凭空发明外部业务标准或跳过最终确认。

## 5. 提问与新手输出

按以下顺序推进，仅询问缺失内容：

1. 目标、目标用户和成功标准；
2. 专家类型与角色结构；
3. 各角色职责与边界；
4. 输入、输出、是否声明 workflow；若声明，再确认 Phase、对应 commands、handoff 和返工；
5. 统一 skills、来源、完整名称及角色分配；
6. 质量门、运行能力、权限和环境依赖。

优先使用当前宿主提供的 ask-user-question 工具。工具支持批量问题时，每轮最多组织 3 个
紧密相关、互不依赖的问题；按实际需要用户回答的决定计数，不按编号数量计数。每一个编号或
工具 question 对象只能包含一个需要回答的问题，不得用一个编号拼接多个问句。不要为了凑数
加入次要问题。如果后一个问题的选项取决于前一个答案，必须分轮询问。工具不可用时，每次只问
一个简短问题。

能从上下文得到的答案直接写入事实清单。用户不熟悉专家结构时，不要求其填写 schema；先给出
业务语言的推荐方案，再请其选择或修订。

默认回复固定为三层：

```markdown
## 我理解的需求
...

## 建议方案及原因
...

## 只需你确认的事项
1. ...
```

正文先说“资料库、能力包、共享规则、稳定流程、快捷入口、计算工具、过程控制、外部连接”等
白话名称，技术名只在第一次出现时括注一次。每轮最多三个实际问题，每项只问一个决定。Schema 字段、JSON 路径、哈希、
receipt、sidecar、权限和自主度枚举统一放到“开发细节”；用户没有要求时不展开。

校验失败先写清问题、对结果的影响和建议动作，再把原始 finding 放进开发细节。不要删除合同、
财务、医疗等业务本身需要的专业词，只降低 Agent 工程术语密度。

## 6. 候选方案

没有实质分歧时给出一个推荐候选。存在会显著改变角色数量、职责边界、工作流、权限或成本的
分歧时，给出 2–3 个真实可行的方案，并说明取舍与推荐理由。

用户说“你来决定”“不要问，直接做”时，可以代为补齐候选设计，但仍需展示最终确认稿。
这种授权不能替代设计确认，也不能替代覆盖、安装升级或 zip 替换的 `--force` 确认。

## 7. 专家设计确认稿

澄清完成后按以下结构展示：

```markdown
# 专家设计确认稿

## 类型与目标
- 类型：expert / team
- 目标：...
- 目标用户：...
- 成功标准：...

## 角色与职责
| 角色 | 定位 | 核心职责 | 不负责 | 输入 | 输出/委派条件 |
|---|---|---|---|---|---|

## 工作流
- 顶层 Workflow：无 / ...
- 无 Workflow 时：Todo 只跟踪普通执行步骤，不建立声明式 Phase。

## 自主度与执行约束
| Workflow / Phase / Agent override | 自主度 | 执行器 | 执行标准 | 验收标准 | 提高自主度原因 |
|---|---|---|---|---|---|
| ... | 极低 / 低 / 中 / 高 / 极高（括号内标底层枚举） | ... | ... | ... | 无 / ... |

若顶层 Workflow 为“无”，本表写“无正式 Workflow；权限使用 no-workflow-bounded-default”，
不要为填表虚构 Phase。

## Commands
| 对应 workflow | command | 入口 agent | 动态文字 | 文件与多模态输入 |
|---|---|---|---|---|
| ... | `/example-command` | primary agent / 团长 | `$ARGUMENTS` | `@path` 或同一次调用中可访问的附件 |

## Skills
| 完整技能名 | 来源 | 编辑策略 | 分配角色 | 作用 | 触发时机 | 预期产物 |
|---|---|---|---|---|---|---|

## 运行能力与权限
- Agent 运行参数：`steps`；按需列出 model / variant / temperature / top_p / hidden / options，未声明项写“继承默认值”...
- References / 资料库：无 / alias、来源、使用角色、何时查阅；Git 来源另列 branch 与能力状态...
- 角色规则：无 / alias、使用角色和规则来源...
- Plugins / hooks：无 / 事件、行为和依赖...
- Custom tools：无 / 工具名、输入输出和权限...
- Workspace instructions：无 / `.opencode/instructions/<slug>/...` 与 `opencode.json.instructions`...
- MCP / 其他 runtime extensions：...
- 权限与环境变量：...

## 质量与异常
- 质量门：...
- 返工、升级和异常处理：...

## 信息来源
- 用户事实：...
- 候选设计：...
- 未确认项：无 / ...
```

最后明确询问：“是否确认按此设计开始生成？”只有用户明确同意，才能创建 manifest 或调用
生成器。输入已经完整时可以直接展示此确认稿，不必人为增加多轮提问。

command 是可选的用户入口，不是 workflow 本体的第二份真相源。为每个可由用户直接触发、会重复
使用的稳定 workflow 默认推荐一个 `workflows[].command`；多个这类 workflow 分别推荐多个 command。内部
handoff、单个 phase 和一次性流程不单独创建。用户明确不需要 command 时，在确认稿中写明原因，
不要让 validator 或生成器自动补建。

## 8. 结构性修改

先展示设计差异：

```markdown
| 设计项 | 修改前 | 候选修改后 | 原因与影响 |
|---|---|---|---|
```

确认后修改 `expert.json` 并整体重建派生物。用户在确认后又改变角色、workflow、skills 或权限时，
返回澄清阶段，更新差异与确认稿后再次确认。

旧包使用 `common_skills` 和 purpose 对象时，结构性修改必须先迁移：不重命名、不改写现有技能
文件，把旧通用技能分配给全部角色，把旧角色技能保留给原角色，再基于统一技能池继续设计。
`origin: uploaded` 且 `edit_policy: preserved` 的技能默认不得修改；若用户明确授权修改包内副本，
确认稿必须展示其将转为 `managed`，同时保留 `origin: uploaded`。

## 9. 阻塞与冲突

- 用户答案互相矛盾：指出冲突并询问，不自行选择。
- 用户暂时无法回答：给出推荐候选并标记来源，不把候选描述成事实。
- 用户拒绝确认：停止生成，可以继续展示或修订草案。
- 目标已存在：设计确认后再处理独立的 `--force` 覆盖确认。
- 诊断中发现需要产品决策：先完成只读报告；若用户要求修复，再转入结构性修改流程。
